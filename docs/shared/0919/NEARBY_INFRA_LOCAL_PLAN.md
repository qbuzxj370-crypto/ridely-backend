# 현위치 주변 인프라 (폰에서 거르기) 작업 계획 (2026-09-19)

브랜치: 백엔드 `feature/poi-all-api`(main 기준), 프론트는 API 다음 단계에서 별도 브랜치
관련: `docs/shared/0918/LOCATION_PRIVACY_ARCHITECTURE.md`, `docs/shared/0919/TOUR_INFO_FRONTEND_PLAN.md`(「이번 범위에서 제외」 표에 있던 항목을 이 문서로 이어받음)

## 목표

내 GPS 위치 주변의 급수대·화장실·수리소 같은 인프라를 보여준다. **위치를 서버로 보내지 않는다.** 그래서 서버에 「내 근처」를 묻지 않고, **서비스 지역의 시설 전체를 한 번 받아 폰에서 GPS로 거른다.** 요청에 위치 정보가 없으므로 「프론트에서만 위치정보가 돈다」는 원칙(자문 확인 사항)을 지킨다.

## 범위

1. **백엔드: 서비스 지역 시설 전체 조회 API 신규** — 기존 `/api/v1/pois/nearby`는 **그대로 둔다**(홈 화면이 지금 쓰는 API)
2. **프론트: 데이터 받아 저장 + GPS로 반경 필터 + 홈에서 표시**

이번에 하지 않는 것: 라이딩 화면의 주변 시설 표시, 자유 주행 사고다발지 경고, 관광지 전체 조회(개요가 길어 별도 설계 필요). 데이터 구조를 같이 쓰므로 나중에 얹기 쉽다.

## 1. 백엔드 API 설계

- 경로: `GET /api/v1/pois/all` (가칭). `PUBLIC_PATHS`의 `/api/v1/pois/**`에 이미 포함돼 인증 설정 변경 없음
- **파라미터 없음.** 좌표·반경·격자·「내 근처」 같은 위치 단서를 받으면 안 된다. 항상 같은 전체 목록을 준다 — 이게 위치정보를 안 받는다는 계약 자체다
- 응답: `{ items: [...], totalCount }`. 새 응답 DTO 필요(기존 `PoiNearbyResponseDTO`는 중심 좌표가 필수). 항목은 `PoiItemDTO` 재사용, `distanceM`은 비워둔다(전역 `non_null`이라 응답에서 빠짐)
- **슬림 응답**: 지도에 점을 찍고 이름을 보여줄 필드만 — 종류(`type`)·번호·이름·좌표·시설 세부종류(`facilityType`)·사고다발지 위험도(`dangerLevel`). **사고다발지 폴리곤(`polygonGeoJson`) 등 무거운 필드는 뺀다**
- 종류: `ROUTE_FACILITY`(WATER·TOILET·CERT_CENTER·AIR_PUMP), `REPAIR_SHOP`, `BIKE_STATION`, `ACCIDENT_ZONE`. 적재 건수는 따릉이 3,239·공기주입기 1,163·화장실 688·급수대 185·사고다발지 111·인증센터 88·수리소 24, 합 약 5,500건
- DAO: 기존 `*InRadius` 조회에서 `ST_DWithin`·거리 계산·`LIMIT`을 뺀 전체 조회를 종류별로 추가(`PoiSpatialDao`, `AccidentZoneSpatialDao`). 기존 메서드는 건드리지 않는다
- **캐시**: 적재 후에만 바뀌는 데이터라 `Cache-Control`(예: 1시간)과 ETag를 붙인다. 앱이 매번 전체를 받지 않게 하는 핵심 장치
- **크기 안전장치**: 테스트로 건수·직렬화 바이트 상한을 고정해 어느 날 갑자기 커지는 걸 CI에서 잡는다

### 데이터가 늘면 (`TOUR_INFO_FRONTEND_PLAN.md`에 정리한 내용 요약)

이 방식은 항상 전부 받아야 하므로 서비스 지역이 넓어질수록 모든 사용자의 다운로드가 선형으로 커진다. 그래서 위 슬림화·캐시·크기 테스트를 처음부터 넣고, `localStorage`(약 5MB)가 모자라지면 `IndexedDB`로 옮긴다. 전국 규모가 되면 DB를 매번 치는 대신 적재 후 만들어둔 정적 파일(CDN)로 내려주는 쪽을 검토한다.

## 2. 프론트 설계

- `js/infra-store.js`(신규): `GET /pois/all`을 받아 `localStorage`에 저장(받은 시각과 함께), 만료 전엔 저장본을 쓰고 만료됐거나 없으면 받는다. 네트워크가 실패하면 만료된 저장본이라도 쓴다
- 필터: 기기 GPS(`navigator.geolocation.getCurrentPosition`)와의 거리를 `haversineM`으로 계산해 반경 안만, 가까운 순으로. **서버로 나가는 요청에는 위치가 없다**
- 홈: 「내 주변 인프라」 버튼 → GPS를 한 번 읽어 그 주변 반경의 시설 마커를 표시하고 내 위치로 지도 이동. 종류 체크박스는 기존 것을 재사용
- 기존 「이 위치 주변 검색」(지도 중심 기준, 서버 조회)은 그대로 둔다

## 결정이 필요한 것 / 확인 사항

1. **위치정보 동의 문구**: 지금 회원가입 문구는 「**라이딩 중** 위치정보(GPS) 수집·이용에 동의합니다」다. 홈에서 현위치를 쓰면 라이딩 밖의 이용이라 **문구를 넓혀야 할 수 있다**(자문 범위 확인 필요). 서버로 안 보내는 점은 그대로
2. **브랜치·PR 순서**: 백엔드 API를 먼저 별도 PR로 병합하고, 프론트는 그 뒤에 이어서 한다(프론트가 홈 화면을 건드려 `feature/tour-info-frontend`와 파일이 겹침 → 그 PR이 먼저 병합돼야 충돌이 없다)
3. **관광지**는 이번 범위에서 뺀다(개요가 길어 전체 조회에 넣으면 무겁다). 필요하면 슬림 목록 API를 따로 설계

## 실측 결과 (2026-09-19, 로컬 DB 실데이터로 이 브랜치 서버를 띄워 확인)

| 항목 | 값 |
|---|---|
| 건수 | 4,479건 (공기주입기 1,100 · 따릉이 3,244 · 사고다발지 111 · 수리소 24). 로컬 DB에는 급수대·화장실·인증센터가 적재돼 있지 않아 실서버 건수(약 5,500)와 다르다 |
| 원본 크기 | 524,815B (항목당 평균 117B) |
| **gzip 전송 크기** | **약 108KB** (원본 대비 약 79% 감소) |
| 응답 시간 | 약 0.14~0.24초 |
| 캐시 | `Cache-Control: max-age=3600, public` + 약한 ETag, 같은 ETag로 재요청 시 **304 (본문 0B)** |

### 실측으로 찾은 문제 — ETag가 gzip을 꺼버렸다

처음엔 ETag가 **강한(strong) 형태**여서 Tomcat이 이 응답을 **압축하지 않았다**(Tomcat은 강한 ETag가 붙은 응답을 압축하지 않는다 — 압축하면 바이트가 달라져 강한 ETag의 의미가 깨지기 때문). 같은 서버의 `/pois/nearby`는 gzip이 되는데 `/pois/all`만 525KB가 그대로 나갔다. **MockMvc 통합 테스트에는 Tomcat 압축이 없어서 테스트로는 못 잡았고**, 실제 서버를 띄워 헤더를 보고서야 발견했다.

조치: `ShallowEtagHeaderFilter`를 약한 ETag(`W/"..."`)로 설정(`HttpCacheConfig`). 조건부 요청(304)은 약한 ETag로도 동일하게 동작한다. 재발 방지로 `PoiAllTest`가 ETag가 `W/`로 시작하는지 고정한다.

### 배포 후 확인할 것 (로컬로는 못 보는 것)

- 실서버는 CloudFront를 거친다. 배포 뒤 `https://<CloudFront>/api/v1/pois/all`에서 **`Content-Encoding: gzip`이 유지되는지**, **`ETag`·`Cache-Control`이 살아 있는지**, 같은 ETag로 재요청 시 **304**가 오는지 확인한다(CloudFront 캐시 정책이 `Accept-Encoding`/`If-None-Match`를 어떻게 다루는지에 달려 있다)
