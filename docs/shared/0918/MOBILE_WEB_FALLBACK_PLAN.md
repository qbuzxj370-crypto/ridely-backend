# 모바일 웹페이지 버전 작업 계획 (2026-09-18)

## 배경 / 목적

스토어(구글 플레이·원스토어) 등록에 차질이 생겼을 때를 대비해, 지금 Cordova로 패키징해 APK로 배포하는 프론트(`android-shell/www/`)를 **모바일 Chrome에서 URL로 바로 접속해 쓰는 웹페이지**로도 돌아가게 만든다. 브랜치: `feature/mobile-web-fallback`.

## 조사 결과 — 생각보다 적게 고치면 된다

`android-shell/www/`를 전수 조사한 결과, Cordova 전용 API(`cordova.exec`, 네이티브 플러그인 JS 등)에 의존하는 코드가 **거의 없다**. 이미 표준 웹 API 위주로 짜여 있다:

| 기능 | 사용 API | 웹에서 그대로 되는가 |
|---|---|---|
| GPS (`riding.js`) | `navigator.geolocation` (표준 API) | ✅ 됨. `cordova-plugin-geolocation`이 설치돼 있지만 이 플러그인은 네이티브 환경에서 표준 API를 그대로 구현해주는 것뿐이라, 플러그인이 없는 웹에서는 브라우저 내장 Geolocation API가 알아서 대신함 |
| 로컬 저장(`ride-storage.js`, `token-store.js` 등) | `localStorage` (표준 API) | ✅ 됨 |
| 지도 | 카카오맵 JS SDK (`<script>` 로드) | ✅ 됨 (단, 도메인 화이트리스트는 새로 등록 필요 — 아래 "열린 질문" 참고) |
| 안드로이드 하드웨어 뒤로가기 | `backbutton` 커스텀 이벤트 (Cordova 전용) | 이벤트 자체가 웹에선 안 뜸 — 근데 우리 라우터가 `location.hash` 기반이라 해시 변경마다 브라우저 히스토리에 쌓여서, 모바일 브라우저의 기본 뒤로가기가 **아무 코드 없이 이미 똑같이 동작**함 |

**딱 하나, 실제로 막는 게 있다**: `www/js/app.js`가 `deviceready` 이벤트를 무조건 기다리는데, 이 이벤트는 Cordova 네이티브 브릿지(`cordova.js`)가 있어야만 발생한다. 오늘 낮에 정적 서버로 직접 테스트해보다가 이것 때문에 화면이 완전히 빈 채로 멈추는 걸 이미 직접 확인했다 — `cordova.js`가 404여도 모듈 스크립트 실행 자체는 막히지 않지만, `deviceready`를 영영 못 받아서 라우터가 시작을 안 한다.

## 설계 방향 (검토 요청)

### 방향 A — 코드베이스 하나 공유 (추천)

`www/` 폴더 하나를 그대로 두고, Cordova 빌드와 웹 배포 양쪽에 다 쓴다. `app.js`만 아래처럼 분기:

```js
if (window.cordova) {
  document.addEventListener('deviceready', onDeviceReady, false);
} else {
  onDeviceReady(); // 웹: cordova.js가 없으니 곧바로 시작
}
```

`index.html`의 `<script src="cordova.js">`는 그대로 둔다 — 실제 Cordova 빌드 때는 빌드 시스템이 진짜 `cordova.js`를 그 자리에 생성해서 넣어주고(레포에는 없음, gitignore 대상), 웹으로 그냥 열면 이 한 줄이 404 나는 것뿐이라 콘솔 에러 하나 빼고는 무해하다. 즉 **코드 변경은 사실상 `app.js` 몇 줄이 전부**고, 유지보수할 코드베이스가 늘어나지 않는다.

### 방향 B — www 폴더를 통째로 복제해서 웹 전용 사본을 따로 관리

앱과 웹을 앞으로 다르게 발전시킬 계획이 있다면 이쪽이 맞을 수 있다. 대신 지금부터 모든 화면 변경을 두 곳에 중복 적용해야 해서 드리프트(둘이 슬금슬금 달라지는 것) 위험이 생긴다.

**→ A로 진행할 예정. 이견 있으면 알려주세요.**

## 작업 항목

1. `app.js`: `deviceready` 대기를 `window.cordova` 유무로 분기
2. (선택) `www/js/index.js` 삭제 — `cordova create` 템플릿이 만든 죽은 파일, 어디서도 안 씀. 이번 작업과 무관하지만 발견한 김에 같이 정리할지 결정
3. 로컬 정적 서버 + Chrome 모바일 에뮬레이션으로 8개 화면 전부 왕복 테스트 (홈/인증/코스추천/코스결과/저장경로/라이딩/라이딩이력/마이페이지)
4. 버그 수정 (테스트 중 발견되는 대로)
5. 로직 검토
6. 최종 정리 + 문서(`FRONTEND_ISSUES.md`, 이 문서) 갱신

## 열린 질문 (진행 전 답 필요)

1. **호스팅 위치**: 이 웹 버전을 어디에 올릴지 아직 안 정해짐 — EC2에서 정적 파일로 같이 서빙할지, 별도 정적 호스팅(Netlify/Vercel/S3 등)을 쓸지. 지금 단계에서는 로컬 개발/테스트만 하고, 실제 배포 주소가 정해지면 그때 `api.js`의 `API_BASE`·`index.html`의 CSP를 맞추면 됨(기존에 이미 문서화된 "배포 시 바꿔야 하는 3곳" 패턴과 동일).
2. **카카오맵 JS 키 도메인 등록**: 지금 앱 origin은 `https://localhost`(Cordova 전용)로 등록돼 있음. 웹 배포 도메인이 정해지면 카카오 개발자 콘솔에 그 도메인도 추가 등록해야 지도가 뜸.
3. **PWA(홈 화면에 추가, 오프라인 등) 지원 여부**: 지금 요청은 "Chrome에서 되는 모바일 웹페이지"라 최소 요건은 아니라고 보고 이번 범위에서 뺐음. 필요하면 `manifest.json` + 아이콘 추가로 별도 작업.
4. **iOS Safari 지원 여부**: 요청에 "Chrome"만 명시돼 있어 안드로이드 Chrome 기준으로만 작업하고 iOS/Safari는 범위 밖으로 둠. 필요하면 알려주세요.

## 남는 리스크

- 카카오맵 JS SDK가 `unsafe-eval`을 요구하는 CSP는 웹에서도 그대로 필요 — 보안적으로 이상적이진 않지만 지도 기능을 쓰는 한 불가피(기존 앱 버전과 동일 제약).
- 실제 모바일 기기의 Chrome에서의 최종 확인은 로컬 에뮬레이션만으로는 100% 대체 못 함 — 실기기 테스트 필요.
